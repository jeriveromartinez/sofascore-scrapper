## Architecture

```
┌──────────────────────────────────────────────────────────┐
│                     nginx (:80)                          │
│                 (multi-instance only)                    │
└────────────┬──────────────┬──────────────┬──────────────┘
     ┌───────┴──────┐ ┌─────┴──────┐ ┌─────┴──────┐
     │  backend-1   │ │ backend-2  │ │ backend-3  │
     │   :8080      │ │  :8080     │ │  :8080     │
     └───┬────┬─────┘ └──┬────┬────┘ └──┬────┬────┘
         │    │          │    │         │    │
         └────┼──────────┼────┼─────────┼────┘
              └──────────┼────┼─────────┘
                    ┌────┴────┴────┐
                    │ MariaDB 10.11│
                    └──────┬───────┘
                    ┌──────┴───────┐
                    │  Redis 7     │
                    └──────────────┘
```

All backends share one MariaDB and one Redis instance. Scheduled jobs
(scrape, stats, upload cleanup, download counter flush) use Redis
distributed locks to prevent duplicate execution.

The Vue SPA is served directly by each backend from `web/dist/`.

## Stack

- **Backend:** Go 1.25, Gin, GORM (MariaDB), go-redis, golang-migrate,
  robfig/cron.
- **Frontend:** Vue 3, Vite, Pinia, TypeScript, Playwright (E2E),
  Vitest (unit).
- **Infrastructure:** Docker (multi-stage), nginx, Prometheus.
- **Scraper:** `chromedp` for SofaScore HTML rendering.
- **Wire format:** Protocol Buffers v3 (`proto/api.proto`); Go bindings
  generated by `protoc-gen-go`, TS bindings by `ts-proto`.

## Local development setup

### Prerequisites

- Go 1.25+
- Node.js 22+ (for the Vue dashboard)
- MariaDB 10.5+ and Redis 5.0+ (the dev Compose file provides both)
- Docker (used for the `.deb` builder and for integration tests)

### Option A — Docker Compose (recommended)

```bash
docker compose -f deployments/docker/compose.dev.yml up --build
```

Brings up MariaDB, Redis, and one backend instance. The backend listens on
`:8080`, and the dashboard is served at <http://localhost:8080>.

Requires `.env` with `JWT_SECRET` set. Copy `.env.example` to `.env` and
fill it in.

### Option B — Run the backend natively

Useful when iterating on Go code without a full container rebuild.

```bash
export DB_HOST=localhost
export DB_PASSWORD=yourpassword
export JWT_SECRET=your-secret-at-least-32-chars
go run ./cmd/server
```

Migrations run automatically on startup (`golang-migrate` embedded via
`go:embed`).

### Option C — Frontend hot-reload

```bash
cd web
npm ci
npm run dev
```

The Vite dev server proxies `/api` to the backend running on `:8080`.

### Bootstrap the first admin

The first user to register becomes admin automatically. To generate the
bootstrap invitation token (only valid while the `users` table is empty):

```bash
go run ./cmd/server bootstrap-invitation
```

Then register via `POST /api/web/v1/users/register` (email + password +
the token).

## Testing

### Go

```bash
go test -race ./...
go test -coverprofile=coverage.out ./...
go vet ./...
```

Race detection is enabled by default in CI. The `internal/testing/`
package provides shared fixtures (DB sandbox, fake clock, fake Redis).

### Frontend

```bash
cd web
npm run lint
npm run test:unit      # Vitest
npm run test:e2e       # Playwright (requires a running backend)
npm run build          # Production bundle
npm run bundle-budget  # Fail if bundle exceeds the budget
```

### Integration tests

```bash

docker compose -f deployments/docker/compose.test.yml run backend-init
docker compose -f deployments/docker/compose.test.yml up backend
```

See [`../performance/load-test.md`](../performance/load-test.md). The k6
scenarios are gated in CI by the `load.yml` workflow; PR-time smoke is the

## Protobuf contract

`proto/api.proto` in this repository is the **single source of truth** for
the HTTP wire format. Two consumers depend on it:

1. The Go backend (`internal/gen/`) — regenerated via `make proto`.
2. The Flutter TV client (`../flutter-apptv/proto/api.proto`) — must be a
   verbatim copy; verified by `make proto-verify-flutter`.
3. The Vue dashboard (`web/src/`) — TypeScript bindings via `ts-proto`
   (`cd web && npm run proto`).

### Working with the proto

```bash
# Regenerate Go bindings from proto/api.proto
make proto

# Verify Go bindings are up to date (CI runs this on every PR)
make proto-check

# Verify the Flutter client mirrors this repo (run before opening a PR)
make proto-verify-flutter
```

### Adding or changing a field

- **Never reorder field numbers and never reuse a deprecated number.** Field
  numbers are the wire-format contract; clients in the wild depend on them.
- For a breaking change, add a new field and deprecate the old one rather
  than editing in place.
- After any proto change, run `make proto` **and** copy the file to the
  Flutter client before regenerating both sides.

The integration-audit roadmap
([`../integration-audit-roadmap.md`](../integration-audit-roadmap.md))
tracks the current cross-repo drift and the plan to close it.

## HTTP API reference

**Auth column:** `None` public · `Token` download-token capability ·
`Device` registered-device header (`APP-XIPTV`) · `Auth` JWT bearer (any
user) · `Admin` JWT bearer with the `admin` role.

### Infrastructure

| Path | Auth | Description |
|---|---|---|
| `GET /` | None | SPA dashboard |
| `GET /health/live` | None | Liveness probe |
| `GET /health/ready` | None | Readiness probe (DB + Redis) |
| `GET /metrics` | None | Prometheus metrics (blocked at the edge in multi-instance; see `nginx.conf`) |

### App API (`/api/app/v1`) — consumed by Android devices

| Method / Path | Auth | Description |
|---|---|---|
| `GET /update` | None | Latest APK version / update check |
| `GET /apk/download/:token` | Token | Download APK by capability token |
| `GET /devices/url/:packageName` | None | Resolve distribution domain for a package |
| `POST /devices` | None | Register device |
| `POST /devices/viewing` | Device | Report playback / viewing |
| `GET /current-events` | Device | Current + upcoming events for the device |
| `POST /crash-report` | None | Submit crash report (IP rate-limited, body-size capped) |
| `GET /teams/logo/:teamId` | None | Team logo image |

### Management API (`/api/web/v1`) — dashboard / operators

| Method / Path | Auth | Description |
|---|---|---|
| `POST /users/register` | None | Register (requires a valid invitation token) |
| `POST /users/login` | None | Obtain access + refresh tokens |
| `POST /users/refresh` | None | Rotate access + refresh tokens |
| `POST /users/logout` | Auth | Revoke refresh token(s) |
| `POST /users/invitations` | Admin | Create an invitation token |
| `PUT /users/:id/role` | Admin | Set a user's role (`admin`/`user`); refuses to demote the last admin |

Every other `/api/web/v1/*` route requires **Admin** — user, device, event,
playback, APK (including resumable uploads), tournament, domain, and
global-config management, plus reporting (`GET /stats/top-events`). See
`internal/app/routes.go` for the authoritative list.

### Query parameter notes

- `GET /api/web/v1/events?date=YYYY-MM-DD` — `date` is parsed as
  **midnight-to-midnight UTC** (`time.Parse("2006-01-02", date)`). An
  operator outside UTC sees events for the previous/next day at the
  boundary; convert to UTC before passing the value. Other query
  parameters (`sport`, `page`, `limit`) are local to that endpoint; see
  the handler for details.

## Authorization & roles

The management API uses JWT bearer authentication (`AuthMiddleware`) plus
role-based access control:

- **Roles:** `admin` and `user` (`users.role`, default `user`).
- **Admin gate:** `RequireAdmin` runs after authentication on every
  `/api/web/v1/*` management route and on invitation creation;
  non-admins receive `403`.
- **Middleware order:** authenticate → rate-limit (fail-closed) → admin
  check, so an unauthenticated flood is throttled before any database
  lookup.
- **Bootstrapping:** migration `000008_user_roles` adds the column and
  promotes every pre-existing account to `admin` (they were implicit
  operators). New invited accounts default to `user`.
- **Promoting / demoting:** `PUT /api/web/v1/users/:id/role` (admin only);
  the last remaining admin cannot be demoted. Inspect roles directly with
  `SELECT email, role FROM users;`.

## Scheduled jobs

| Job | Schedule | Lock TTL |
|---|---|---|
| Scrape today | Every 1 minute | 10 min |
| Scrape future | 06:00 and 18:00 UTC | 30 min |
| Daily content stats | 00:01 UTC | 10 min |
| Monthly content stats | 00:10 on 1st | 30 min |
| Upload cleanup | Every 15 minutes | 10 min |
| Download counter flush | Every 15 minutes | 10 min |

All jobs use distributed Redis locks to prevent duplicate execution across
instances. If a lock cannot be acquired, the job is silently skipped.
Detailed job matrix and Redis outage behavior are documented in
[`../operations/runbook.md`](../operations/runbook.md#scheduler-job-matrix).

## Conventions

### Go

- Standard `gofmt` formatting. CI fails on unformatted code.
- Imports: standard library → third-party → internal (`internal/...`),
  separated by blank lines.
- Errors are returned, not swallowed. Use `fmt.Errorf("...: %w", err)`
  to wrap; use `errors.Is` / `errors.As` to inspect.
- No panics on the request path. `panic` is acceptable only at startup
  for unrecoverable configuration errors.
- Tests live next to the code (`foo_test.go`). Use table-driven tests
  when there are >2 cases for the same function.
- Shared test helpers live in `internal/testing/`.

### Shell

- `#!/usr/bin/env bash` + `set -Eeuo pipefail` for non-trivial scripts.
- LF line endings everywhere (enforced via `.gitattributes`); Windows
  checkouts with `core.autocrlf=true` will otherwise break scripts that
  are mounted into Linux containers.
- Prefer existing helpers over introducing new ones; ask before adding a
  dependency.

### Migrations

- Sequential numeric prefix (`000001_baseline.up.sql`, etc.).
- Every `.up.sql` MUST have a paired `.down.sql`.
- **Destructive** migrations (data loss) must have an empty `.down.sql`
  to prevent accidental reversal. See
  [`../operations/rollback.md`](../operations/rollback.md) for the policy
  and the pre-migration checklist.
- Migrations are embedded in the binary via `go:embed` and run on startup
  using `golang-migrate/v4`. Forward only.

### Commit messages

- English, present tense, imperative.
- Conventional Commits: `type(scope): imperative summary`. Types:
  `feat`, `fix`, `chore`, `refactor`, `docs`, `test`, `build`, `ci`.
- Subject line under 72 characters.
- One logical change per commit; never bundle refactor + bugfix + format
  pass.

### Branching

- Branch off `main`, never off feature branches.
- Type-prefixed kebab-case names: `feat/...`, `fix/...`, `chore/...`,
  `refactor/...`, `docs/...`, `test/...`.
- Rebase before pushing; squash fixup commits.
- Open the PR against `main` once the local test suite and `go vet` pass.
